## 1. レビュー総評

* **対象ドキュメント**: docs/design/基本設計書_概要.md（基本設計書（概要））
* **アプローチ**: 新規設計
* **判定結果**: 差し戻し (Needs Revision)
* **全体サマリー**: 要件定義書 v1.1 と NOUS-18 の決定を漏れなく取り込み、管理サーバーを 127.0.0.1 に置いて Q-322 の決定を構成で担保した点、試行ごとに利用量を記録して上限停止に結びつけた点は優れている。一方で、停止の反映時間・世界内時間・無料枠の集計の単位に、要件と矛盾する設計が3点ある。いずれも実装すると要件違反になるため、差し戻す。

## 2. 要件との整合性・網羅性チェック

* **要件のトレース**: MVP の FR（Must・Should の MVP 分）、BT-001〜005、IF-001、NFR-L・S の主要項目は付録の対応表で追える。FR-302 の活動量、FR-306 の世界内時間、FR-217 の矛盾の記録も機能として定義されている。
* **ドキュメント間の整合性**: 画面一覧は SC の MVP 分をすべて含み、P106・P208・P211 を追加している。追加の理由（招待の失敗時の案内、生成ログの詳細、アーカイブの参照）は要件から導ける。
* **オーバースペックの有無**: 並列数の上限を 1〜3 で設定可能にしているが、既定は 1 で、要件（FR-403）の範囲である。過剰な設計は見当たらない。

## 3. アーキテクチャ・技術的妥当性チェック

* **データモデルの妥当性**: world_id を全データに持たせてアーカイブを同じ DB に残す方式は、FR-303 を単純に満たす。ただし daily_usage を世界ごとに持つため、同じ利用日の中でリセットすると、新しい世界の集計が 0 から始まり、アカウント単位の無料枠（1日 10,000 Neurons）を超えて生成を続けてしまう（指摘 M-03）。
* **処理ロジック・インターフェース**: 世界内時間を world_elapsed_sec と running_since で持つ方式は妥当だが、プロセスが稼働のまま終了した（端末のスリープ・強制終了）場合、起動時に running_since からの経過がそのまま加算され、止まっていた時間が世界内時間に入る。B07 の「止めた時点の値から続ける」を実現する手段が定義されていない（指摘 M-02）。
* **コンポーネント設計**: 観察画面と管理画面を別ビルドにした分離は妥当。

## 4. 非機能要件・異常系設計のチェック

* **エラーハンドリング**: 一時停止・上限到達の後も、再試行の待ち（30 秒・120 秒）を続ける設計になっている。NFR-P-006（Q-317 の決定）の「実行中の生成は最大 60 秒で終わる」と矛盾する（指摘 M-01）。
* **セキュリティ・可用性**: 管理サーバーのバインド先の固定、招待トークンのハッシュ保存、CSRF、CSP、私設アドレスの検査がそろっている。観察サーバーは 0.0.0.0（IPv4）だけで待ち受けるため IPv6 からは到達しないが、要件上の問題はない（指摘 I-01）。

## 5. 記述の網羅性・粒度・曖昧さの評価

* **網羅性とフォーマット遵守の監査**: API 詳細定義が 38 件中 16 件にとどまり、残りを一括の記述で済ませている（指摘 M-04）。CRUD 図に view_access_logs の列がなく、注記で済ませている（指摘 m-01）。
* **矛盾点・不明瞭な記述**: 上記 M-01〜M-03 のほかは見当たらない。
* **ロジックと制約の具体性チェック**: 実行設定の範囲と既定値、入力の文字数、セッションの期限、ロックの条件が数値で定義されている。実行回数の既定値 480 の根拠（9,500 ÷ 約 19.1 ≒ 497 から再試行の余裕を引いた値）が本文にない（指摘 m-02）。
* **TBD事項のリスク評価**: Q-105（同時閲覧の人数）は NFR-P-002 の数値だけに影響し、構成は変わらない。リスクは小さい。
* **ステータス・区分値（Enum）の具体性チェック**: worlds.state は 5.7.1 の遷移表で定義されているが、追加した archived への遷移条件が F16 にしか書かれていない。generation_events.status（running・succeeded・failed・cancelled・interrupted）の遷移条件の表がない（指摘 m-03）。

## 6. 具体的な修正指示（アクションアイテム）

* **必須修正項目（Must）**:
  - M-01（Major）docs/design/基本設計書_概要.md 2章 異常系1・4章 B05・8章 性能：世界の状態が稼働以外になったら、再試行の待ちを打ち切って生成イベントを閉じることを定義する。閉じるときの status と failure_kind も決める。
  - M-02（Major）同 6章 worlds・4章 B07：稼働中に一定の間隔で生存の時刻を記録し、起動時はその時刻までを世界内時間に加える方式を定義する。起動時の世界の状態の扱い（稼働のまま続けるか）も決める。
  - M-03（Major）同 6章 daily_usage・4章 F20・B02：Neurons と実行回数の上限の判定を、世界ではなく利用日（アカウント単位）で行うよう、集計の単位を改める。運用指標の世界ごとの値は別に持つ。
  - M-04（Major）同 7章 API詳細定義：一括の記述をやめ、38 件すべての API を個別に定義する。
* **推奨改善項目（Should / Could）**:
  - m-01（Minor）同 6章 CRUD図：view_access_logs の列を足す。
  - m-02（Minor）同 6章 world_settings：実行回数の既定値 480 の根拠を書く。
  - m-03（Minor）同 6章：worlds.state の archived と、generation_events.status の遷移条件の表を足す。
  - I-01（Info）同 8章：観察サーバーが IPv4 だけで待ち受けることを明記する。
  - I-02（Info）同 10章：品質の試行やプロンプトの試行も、本番と同じアカウントの無料枠を使うことを、運用上の注意として書く。
