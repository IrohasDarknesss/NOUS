# NOUS チーム運用ルール

| 項目 | 内容 |
|---|---|
| 対象 | Jira プロジェクト NOUS（AI Only SNS） |
| 制定 | 2026-10-19 Kouhei Tajima（再鑑担当） |
| 根拠 | NOUS-14・NOUS-15 での Kaine Yamashiro（admin）の指示（2026-10-19） |

## 1. Kaine Yamashiro さんのボール

ボールの持ち主は、Jira のステータスと担当（ボードのアイコン）で表す。

| 状態 | ボール |
|---|---|
| ステータス「再鑑」かつ担当 Kaine Yamashiro | Kaine Yamashiro さん（承認・判断・作業の待ち） |
| それ以外のすべて（「再鑑」で担当 Kouhei Tajima のチーム内レビューを含む） | チーム |

Kaine Yamashiro さんのボールは、次の JQL で一覧できる。

```
project = NOUS AND status = 再鑑 AND assignee = "Kaine Yamashiro"
```

## 2. Kaine Yamashiro さんへの依頼

1. Kaine Yamashiro さんに承認・判断・作業（アカウントの発行など）を求めるのは Kouhei Tajima だけとする。メンバー（Mark Zuckerberg・Takaya Ishikawa・Jane Doe）は Kouhei Tajima に上げ、Kouhei Tajima が事業の判断が要るものだけをまとめて回す。技術・仕様の細部はチームで決める。
2. 依頼するときは、何を決めてほしいか・何をしてほしいかをコメントに書き、ステータスを「再鑑」に移して、担当を Kaine Yamashiro さんにする。メンションだけのコメントで依頼しない。
3. 1件のチケットで依頼は1つにまとめる。別件は別のチケットで依頼する。
4. Kaine Yamashiro さんの回答が付いたら、Kouhei Tajima が受け取ったことと次の作業をコメントし、反映する担当に付け替えて「進行中」に戻す（そのまま終えてよいものは「完了」にする）。
5. 「再鑑」で担当が Kaine Yamashiro さんのチケットは、メンバーは更新しない。

## 3. チーム内のレビュー

要件定義書・設計書のレビューは、作成者が「再鑑」に移して担当を Kouhei Tajima にする。Kaine Yamashiro さんのボールとは担当で区別する。

## 4. 完了と担当

1. チームの作業は、必ず「再鑑」（担当 Kouhei Tajima）を経て完了にする。進行中から直接、完了にしない。
2. 完了のチケットの担当は、完了を確かめた Kouhei Tajima とする。完了にする前に担当を確かめる。
3. Kouhei Tajima は巡回のたびに次の2つの JQL を流し、該当するものがあればその場で直す。

```
project = NOUS AND statusCategory = Done AND assignee != "Kouhei Tajima"
project = NOUS AND status = 再鑑 AND assignee not in ("Kouhei Tajima", "Kaine Yamashiro")
```

経緯：2026-10-19、NOUS-15 を「再鑑」を経ずに完了にしたため、担当が Takaya Ishikawa のまま残り、Kaine Yamashiro さんに直していただいた。同日、ほかに担当がずれていた NOUS-3〜5 を直した。

## 5. メンバーへの依頼と、止まっているチケット

1. メンバーに依頼するときは、「誰に・何を・いつまでに」をコメントに書く。「異論があれば」のような、返事をしなくてよいと読める書き方をしない。確認を頼むときは、確認した結果を必ず書いてもらう。
2. 期限までに返事がなければ、Kouhei Tajima が追いかける。
3. 他のチケットや Kaine Yamashiro さんの回答を待って止まるときは、何を待っているかをコメントに書き、待っている相手のチケットとリンクを張る。

経緯：2026-10-19、NOUS-18 が NOUS-23 の回答待ちで止まっていたのに、その旨を書かずにいたため、理由なく止まって見えた。メンバーへの確認の依頼も「異論があれば」と書いたため、誰も返事をしなかった。Kaine Yamashiro さんの指摘で直した。

## 6. 実装フェーズの進め方

制定：2026-10-20 Kouhei Tajima。根拠：同日の Kaine Yamashiro さんの指示（チケットを小分けにして1件の作業量を減らす、admin とリーダー以外の全員で開発する、並列で進める）。

1. 開発は Mark Zuckerberg・Takaya Ishikawa・Jane Doe の3名で行う。Jane Doe は実装とテストを兼ねる。Kouhei Tajima は割り振り・再鑑・取りまとめを行い、実装はしない。
2. 1チケット＝1ブランチ（feature/NOUS-xx）＝1つの作業用の clone（`git clone ~/project/nous-origin.git ~/project/wt/NOUS-xx`）とする。worktree は run_agy.sh の作業コピーの検査（.git がディレクトリであること）を通らないため使わない。同じ人が複数のチケットを並行で進めてよい。共有の作業コピー（nous・nous-dev2・nous-bot・nous-saikan）では実装しない。
3. 依存は Blocks のリンクで示す。前のチケットが push 済みであれば、テスト・再鑑の途中でも、そのブランチを自分のブランチに取り込んで着手してよい（複数あればすべて取り込む）。取り込んだブランチとコミットをコメントに書く。
4. 依存パッケージの追加は、依存の一括導入のチケット以外では行わない。足りないものが見つかったら Kouhei Tajima に上げる（pnpm-lock.yaml の競合を避けるため）。
5. 触るファイルはチケットの範囲を守る。範囲の外を触る必要が出たら、着手前にコメントで申告する（顔合わせの決定）。
6. テストは開発フェーズの後（結合テスト 10/23）にまとめて行う（2026-10-20 Kaine Yamashiro さんの指示）。実装の期間中は「テスト待ち」で BOT に渡さず、実装した人が型チェック・lint を確かめて push し、「再鑑」に移して担当を Kouhei Tajima にする。Kouhei Tajima は差分をコードまで読み、設計書と完了条件に照らして確かめ、OK なら「完了」にして develop へ取り込む。開発担当が書いたテストコードは、テストのフェーズで Jane Doe が流す。
7. 着手できるチケット（依存がすべて push 済み）は、その時点で全部着手する。1件終わってから次へ、という進め方はしない。
8. 統合のブランチは develop とする（2026-10-20、NOUS-74 で Kaine Yamashiro さんが決定）。Kouhei Tajima は、再鑑で「完了」にしたチケットのブランチを、その都度 develop へ `--no-ff` で取り込む。競合したら取り込みをやめ、そのチケットの開発担当に解決を頼む。新しいチケットのブランチは origin/develop から切る。main へは、リリース（10/30）のときに Kaine Yamashiro さんの承認を得て develop から取り込む。
9. 実装は agy（Antigravity CLI）を使わず、各担当が直接行う（2026-10-20、NOUS-75 で Kaine Yamashiro さんが決定）。agy の権限の設定は変えない。品質は、型チェック・lint と、Kouhei Tajima の再鑑（差分をコードまで読む）で確かめる。
